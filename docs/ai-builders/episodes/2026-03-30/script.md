那张截图里是什么？

根据评论区的反应推断，是用户写来的信。有人感谢 Claude 帮他们度过了某段最难熬的时间，有人说 Claude 是他们愿意倾诉的对象之一。做 AI 的人，日常是修 bug、做 code review、优化性能，同时也在接收这些来自陌生人的倾诉。

这条推文之所以有将近七千个点赞，很大程度上是因为它把一件大家心里有感觉、但通常不会明说的事说出来了。我们平时谈论 AI，谈的是参数量、基准分数、API 成本。但在这些数字背后，有一些人的生活已经被切实地改变了。做这件事的人，会以一种工程师职位描述里不会写进去的方式，参与到这个过程中。

Justine Moore 昨天发了一句话，只有几个字，但在时间线上传了很久："我到现在还没从一件事里缓过来——我们现在可以租用智能了。"

把这两件事并排放，你会看到一种奇异的对位：一边是智能变成了按量计费的资源，像带宽、像算力，可以随时订购，随时取消；另一边是，有人在给制造这个资源的工程师写信，说谢谢你。

商品化和情感化，同时在发生，彼此不矛盾。

这没有标准答案，我也不打算给一个。但如果你在这个行业里工作，或者你在用这些工具建东西，Boris 的那张截图是一个有用的校准——你做的事，到底在触碰什么。

换个方向，说今天最实用的内容。

Greg Isenberg 发了一段 46 秒的短视频，标题是"用四个 .md 文件把你的 Claude 提升十倍"。将近 3800 次收藏，是昨天所有内容里保存数最高的。

为什么一个使用技巧会被这么多人保存？因为它直接解决了一个用 Claude Code 的人每天都会遇到的摩擦——每次新开对话，Claude 对你一无所知。不知道你在做什么项目，不知道你的偏好，不知道上次做了什么决定。你得重新解释背景，重新建立上下文。这个摩擦看起来小，但乘以每天十几次对话，消耗就很真实了。

他推荐的四个文件是：CLAUDE.md，放项目概述、技术栈和开发规范；PLANNING.md，放当前的方向和阶段性目标；TASKS.md，放具体的待办事项；还有一个记录个人偏好的文件，比如你希望 Claude 用什么风格写代码、哪些事情不要帮你自动决定。每次新对话，这几个文件就是 Claude 的入职材料，让它直接进入状态，而不是每次都从问"你是谁、你在做什么"开始。

这套做法本身不是新发明，很多重度用户早就在这么做了。Greg 做的事是：把它整理成一套完整的模板，用一个极短的视频讲清楚，降低了上手门槛。有时候，把"大家都在做但没人系统化"的事情写成说明书，影响力比发布一个全新功能还要大。

如果你用 Claude Code 但还没有这几个文件，今天可以花十五分钟建一个 CLAUDE.md，把你目前在做的项目基本情况写进去。成本极低，但可能省下以后很多次重复解释。

说完工具，来聊一个人的故事。

Lenny Rachitsky 昨天发布了一期播客，主角是 Claire Vo。Claire 是 How I AI 的主播，ChatPRD 的创始人。

她第一次用 OpenClaw 的那天，OpenClaw 把她的家庭日历删了。

然后她变成了它最狂热的用户之一。

现在她在三台 Mac Mini 上跑 9 个 agent。

这个故事值得讲，不只是因为"9 个 agent"这个数字看起来够酷。更重要的是，Claire 在此之前是公开的怀疑者。从怀疑到这个程度的投入，中间发生了什么？

她的具体设置是这样的：销售 agent 叫 Sam，每天扫描 CRM，识别新注册用户里的决策者，发出个性化外联邮件——做的是一个之前需要每周雇人工作十小时的活。家庭 agent 叫 Finn，每天下午三点给她和丈夫发一条消息："今天谁接哪个孩子？" 然后自动标记各种日程冲突。还有专门用于播客准备、孩子作业辅助、课程项目管理的 agent，各司其职。

这期播客里有几个概念值得带走。

第一个是她说的"渐进信任模型"：先给 agent 读取日历的权限，然后是读邮件，然后是起草回复，最后才是直接发出。类比是雇了一个新助理，你不会第一天就把所有权限都给他——你观察，你验证，然后逐步扩大授权范围。这个框架对任何刚开始用 agent 的人都有参考价值，它降低了出错的代价，同时也降低了上手的心理负担。

第二个是她对"单一超级助手"的反对。她说，把所有任务都压给一个 agent 是错误的设计思路，不管是效率还是出错风险都更高。正确的方式是像管理 Slack 频道一样——不同职能用专门的 agent 处理，每个 agent 的职责边界要清晰。这也和 Lenny 收到的很多用户反馈呼应：第一次用好的关键，通常是从一个具体任务开始，而不是试图一次接管所有事情。

第三个是今天我觉得最有意思的一个观察：她说，真正做好 agent 这件事，需要的是管理技能，而不是技术技能。你要知道怎么给下属布置任务、怎么设定边界、怎么处理错误和意外情况。技术是入场资格，管理才是核心能力。

这个框架有一个很有趣的推论：有大量没有编程背景、但有管理经验的人，可能比很多工程师更快地用好这些工具——因为他们已经有那套心智模型了。

Claire 说这是她的"ChatGPT 时刻"——从旁观者变成参与者，从"听说很厉害"变成"我正在用、离不开了"。Lenny 的播客在 Shownotes 里，完整版很值得听。

同样是昨天发布的，Peter Yang 和 Claude Cowork 设计负责人 Jenny Wen 的 40 分钟访谈，互动量很高，值得单独说一下。

这期访谈的核心价值不是 Cowork 这个产品本身，而是它提供了一个难得的内部视角：Anthropic 现在是怎么构建产品的。

几个细节。

"我们现在几天就能做完一个功能，而不是几周。" Jenny 在访谈里展示了 Cowork 从最早期原型到现在的完整演变过程——前后迭代了很多轮，方向磨了差不多一年。所以这句话不是在说"我们运气好、第一版就对了"，而是在说：即使经过这么长时间的探索，真正执行的速度依然可以是天级别的。

"以前有里程碑的 spec，现在基本不做了。" Milestone spec 是传统产品开发的基础——写清楚第一周交付什么、第二周验证什么。Anthropic 现在不做了，不是因为他们不重视计划，而是因为迭代速度快到 spec 写完就已经过时了。这是一个工具意识上的真实变化，不是说说而已。

然后她给设计师说了一句话："如果你觉得脚下的地在移动，那是因为它确实在移动。" 不是安慰，不是吓唬。是字面的描述。

40 分钟的访谈，适合周末看，Shownotes 里有链接。
