Claude Code 的插件现在能跑 eval 了，这意味着什么？Replit 收购了一家完全在自己平台上长出来的公司，这个模式能复制吗？Anthropic 的工程师说 AI 写的生产代码应该比人写的更严格，你同意吗？先从最让工程师睡不着的那件事开始。

Claude Code 正式推出了插件 eval 功能。这是给插件开发者的一套测试框架，让你能知道自己写的 plugin 到底有没有用。

Claude Code 团队的 Thariq 昨天解释了推出这个功能的直接原因。他们收到很多反馈，说模型一升级，之前好用的 skill 就不知道还管不管用了。现在你可以在插件目录里跑 claude plugin eval init，创建测试用例，让 agent 带着插件跑一遍，再不带插件跑一遍，对比两次结果。

不过，做 evals 工具出身的 Hamel Husain 很快就给出了很具体的改进建议。他指出，现在这套流程会先问你一堆关于插件体验的回忆型问题，然后自动生成数据集和评判标准。他觉得更好的做法是“原位反馈”——在使用插件的当下就直接标注哪些地方不 work。另外，他还提到对非 plugin 类型的 skill 支持比较别扭，他花了 10 分钟才让 Claude 帮自己配好。

Thariq 在另一条推文里也谈到了一个更根本的问题。他说现在光看 pass/fail 分数基本没法解读 evals，很多 benchmark 里的失败案例其实是隐藏测试条件太苛刻，有时候模型给出的答案比预期结果更合理。

如果你在给 Claude Code 写插件，现在就可以去跑一下 eval init。如果你的插件不是标准 plugin 格式，可能得多花点时间折腾配置。

Replit 的 CEO Amjad Masad 昨天宣布收购了一家叫 Test 13 的公司。有意思的是，这家公司从诞生第一天起就完全跑在 Replit 上。

Test 13 的创始人 Viktor Thulin 写了一段很详细的复盘。18 个月前，他和另一位联合创始人抱着一个简单的信念起步：AI 正在改变软件开发的方式，两个人应该能快速试出一批能赚钱的 SaaS 产品，同时给本地市场提供比传统外包低 60% 到 80% 的价格。结果 18 个月内，他们创造了超过 70 万美元的收入，年增长率超过 400%。

Viktor 在帖子里提到一个细节。他今年早些时候给 Amjad 发了一条私信，说冰岛市场太小了，有时候感觉自己在地理上被隔绝在 AI 创新的前沿之外。他想花下一个十年站在这个变革的中心，而不是在小市场里旁观。几个月后，收购就发生了。

Amjad 在转发时说，他预计这会是“众多案例中的第一个”。这句话挺值得琢磨的。Replit 不只是在卖一个编程工具，它在催生一种新的公司形态——平台上的成功用户本身就是平台的收购标的。

换个方向。Anthropic 的 Boris Cherny 昨天公开了一封他经常回复的邮件模板，在圈子里传了一夜。

事情起因是这样的。Boris 说他每天都会收到类似的问题：AI 生成的代码应该按什么标准来要求？他决定把自己的回复公开出来，让更多人有参考。核心观点很明确：原型代码和一次性代码可以当黑盒用，但生产代码的标准应该比人写的更高。

他的理由是，在 Anthropic 内部，Claude 写的生产代码要经过大量 guardrail——大量的 lint 规则、测试、端到端测试、每天的 fuzz 测试、自动 code review 和安全审查。没有这些，代码库很快就会变成没法维护的烂摊子。

如果 Claude 的代码达不到标准怎么办？Boris 给了几条具体建议：用最新的前沿模型比如 Opus 5 或 Fable 5.1，把 effort 调到 high 或 xhigh，投入时间打磨 CLAUDE.md 和 skills，让模型真正理解你的代码库。如果这些都不管用，就多手动引导 Claude，或者让它重写代码库来降低复杂度。再不行，就等下一代模型。

Meta 的 AI 高级总监 Madhu Guru 从另一个角度呼应了这个话题。他昨天发了 evals 系列的第十篇，标题是“衡量步骤，而不只是结果”。

他举了个例子。两个 agent 轨迹可能都给出了正确答案 42。但一个只用了 4 次工具调用，检索了正确的文档，路径干净。另一个调了 17 次工具，同一个东西搜了三遍，从两次错误中恢复才勉强到达终点。只看最终结果看不出区别，但步骤质量天差地别。

Madhu 的建议是把工作流拆开，定义每一步的任务，为每一步单独设计评估指标。每次看 eval 结果时先看步骤，再看最终答案。

同一时间，Box 的 CEO Aaron Levie 分享了他这周见完几十家企业技术负责人之后的一手观察。他说现在企业 AI 落地有七个核心趋势，其中最突出的是安全问题——Hugging Face 事件之后，企业对 agent 安全和身份管理的关注度明显上升。另外，大多数公司在同时部署多个前沿模型，想标准化但做不到。还有一个反复被提到的问题是 evals，大多数企业对自己工作流的评估还处于非常早期的阶段。

Levies 昨天还宣布了一个产品更新。Box 推出了 Box Mount，让企业 agent 能直接把 Box 里的文档挂载到 agent 的沙箱环境里，用普通的 shell 命令和文件路径来读写，同时保持权限、版本和审计记录。他在演示里展示了一个 agent 挂载了 Box 里的 deal room，读取五份源文件，并行启动三个专家 agent，最后通过 Box Mount 写回四份报告。当客户在 Box 里修改了 MSA 文件后，Box Mount 自动同步新版本，agent 重新评估并刷新所有报告。

Greg Isenberg 昨天把 OpenAI 的 Agents API 比作“agent 的 AWS 时刻”。他说以前建 agent 最难的部分——让它跑好几天不丢状态、记住上下文、调用工具、步骤失败后恢复——现在变成了一个 API 调用。

他的判断是，如果你的公司只是一层 agent 平台，过去一年做的事现在被包含在 token 价格里了。但如果你的壁垒是深耕某个行业的 know-how——比如什么算一个已完成的理赔、什么会让一份申报被驳回、钱从哪里漏掉——那基础设施 commoditize 反而是好事。最难的工程变成了成本项，剩下唯一真正难的是懂业务。

接下来这段我们多说几句。

昨天 Boris Cherny 那封关于 AI 代码质量的邮件模板，引发了超出预期的大范围讨论。这不只是“要不要 review AI 代码”的问题，背后是一个更根本的张力：当代码的边际成本趋近于零，质量标准的锚点应该定在哪里。

Boris 的立场很清晰。AI 写的生产代码要比人写的更严格。他的逻辑不是不信任 AI，而是因为 AI 写代码太快了——快到如果你不设更高的门槛，代码库会在很短的时间内膨胀成没人敢碰的样子。他在 Anthropic 内部的做法是用大量的自动化 guardrail 来兜底，lint、测试、fuzz、自动 review，一层叠一层。

Madhu Guru 的 evals 系列从另一个维度切入了同一个问题。他说只看最终结果没用，得看 agent 是怎么到达那个结果的。这跟 Boris 说的“代码质量要看过程”完全是一个逻辑。一个 agent 用了 4 步干净的调用拿到正确答案，另一个绕了 17 步才勉强到达，表面上结果一样，但后者的代码库会越来越像沼泽。

Peter Yang 在昨天的一条推文里抱怨 Sol 变得“犹豫”了。他让它“现在更新”，它回“我可以更新，但请确认”。只是改一个简单的文档，不涉及删文件。Peter 猜测可能是 harness 或者默认 prompt 改了。这件事跟 Boris 的讨论放在一起看就有意思了——我们在要求 AI 写更高质量的代码，但同时也在抱怨它变得太谨慎、不敢直接执行。

Box 的 Aaron Levie 从企业视角给了一个补充。他说他这周见的几十家企业里，大多数已经在同时部署多个前沿模型，而且“试了 X 不行就换 Y”的速度比以往任何时候都快。没人会等一个供应商把东西做对，不行就直接换。这意味着代码质量的标准不是静态的——它取决于你的模型供应商下个季度还在不在你的技术栈里。

对你的启发可能是这样。如果你在用 AI 写生产代码，现在就应该建一套自动化的质量门禁。不是靠人工 review 来兜底，而是靠 lint、测试、fuzz、自动 review 这些可以批量跑的东西。同时，如果你发现自己的 agent 开始变得“犹豫”——像 Peter 遇到的那样——去检查一下你的 system prompt 和 harness 配置，大概率是那边改了东西。
