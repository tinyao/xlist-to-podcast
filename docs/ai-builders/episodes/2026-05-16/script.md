OpenClaw 项目的 agent 自动化矩阵被 Peter Steinberger 完整公开了。
他昨天发了一条超长推文，回应外界对他 AI 开销的震惊。
他说自己一直在试图回答一个问题：如果 token 成本不再是限制，软件该怎么建？

答案是一套让大部分团队瞠目结舌的自动化流水线。
他同时在云端跑了大约 100 个 Codex 实例，各司其职。
有的 agent 审查每一个 PR 和 issue，代码合入主干后自动回溯六个月前的相关 issue 并关闭。
有的 agent 在每次 commit 时做安全审查，因为人工太容易漏。
有的 agent 做 issue 去重和聚类，自动生成最紧迫问题的报告。

还有更复杂的。
agent 能重现复杂的运行环境，在虚拟机里登录 Telegram，录一段视频，然后把修复前后的对比贴到 PR 里。
有的 agent 监控新 issue，如果符合项目规划方向，直接自动生成 PR，再由另一个 Codex 审查。
有的 agent 扫描评论区删除垃圾信息。
有的 agent 监听会议讨论，一边开会一边自动生成新功能的 PR。

Peter 说，正是这套自动化矩阵，让 OpenClaw 这个项目能以极精简的人力运转。
他昨天还发布了 clawpatch 0.1.0，一个能把代码库拆成语义切片、自动审查 bug 和质量问题的工具。
安装命令是 npm install -g clawpatch。
如果你在思考怎么把 agent 从"辅助写代码"升级到"接管工程流程"，Peter 这套公开的架构值得逐条研究。

另一件值得说的事。
Greg Isenberg 又补了 17 条 agent 观察，接上了两天前那 32 条的讨论。
这次有几个新角度。

他说 Hermes agent 每次完成任务后会自己写记忆。
这意味着今天开始用的人和六个月后开始用的人之间，会形成不公平的优势。
他预测 12 个月内会出现一种 agent，看你工作一周，然后不需要任何指令就能接手你的工作。
屏幕录制加 agent 记忆加本地模型的组合，现在已经能做到了。

本地模型的意义，Greg 给了一个很具体的商业判断。
你可以把 AI 完全跑在客户设备上，永远不碰他们的数据。
零隐私顾虑、零服务器成本、零合规麻烦。
医疗、法律、金融这些受监管行业，一夜之间就打开了。

另一条很实在：YAML 配置文件正在变成新的组织架构图。
谁向谁汇报、有什么权限、能访问什么工具，全写在一个配置文件里。
公司的结构变成了一个可以版本控制、可以 fork、可以部署的文件。
Greg 说这是全新的东西。

他还提了一个容易被忽视的风险。
agent 正在公司内部制造无意识的竞争。
市场 agent 和销售 agent 各自优化不同的指标，互相打架，没人发现。
人类花了数十年才搞明白跨职能对齐，agent 这边完全没想过。

如果你在考虑用 agent 做业务，Greg 这 17 条里有一条特别值得对照。
他说 agent 延迟是新的页面加载速度。
如果你的 agent 45 秒才响应，客户已经切换到另一个 3 秒响应的 agent 了。

角色模糊这件事，昨天有两条线同时推进。
Aaron Levie 写了一篇长文，回应 Lenny 前几天说的"每个人都在用 AI 做别人的工作"。
Aaron 的判断是，AI 确实让大家更容易探索相邻职能，但这只是暂时的混乱。
他的核心观点是，AI 最终会强化专业分工，而不是消灭它。
产品经理应该花大量时间和客户在一起，工程师应该构建可扩展的系统。
现在两者都可以多做一点对方的活，但最终工作量会大到值得重新分工。

而 Elena Verna 写了一篇文章，标题直接说：IC 工作是新的职业炫耀。
Lenny 转发并说很喜欢这个观点。
Elena 观察到，在 AI 时代，能亲自上手的个人贡献者正在重新变得稀缺和受尊重。
这和往期节目里 Julie Zhuo 说的"把品味蒸馏给 AI"是同一条线。
如果你在带团队，Aaron 和 Elena 这两篇放在一起读，能帮你理清一个正在成型的趋势。

今天值得展开聊的，是这件事。

过去 24 小时，有两条线同时指向了同一个方向。
第一条是 Google 的 PM 负责人 Madhu Guru 发的一条推文。
他说整整一代产品经理正在挣扎着适应 AI，因为他们被训练成执行 playbook 的人，而 AI 要求他们发明 playbook。
第二条是 Aaron Levie 和 Elena Verna 关于角色分工的讨论。

Madhu 的推文很短，但很重。
他说过去二十年，只有少数团队在发明产品模式，其他所有人都只是把这些模式搬到自己的领域。
这让大量 PM 工作变得枯燥和机械，但很长一段时间里，这足够建立一份职业生涯。
这也是为什么那么多软件产品长得一模一样。

他的结论是：PM 现在必须是发明家，而不是框架执行者。
没有稳定的 playbook 可以复用。
你不能靠 A/B 测试跑出一个突破性的 AI 产品。
这件事是可以做到的，但 PM 需要忘记过去学的东西。

这条推文的互动数不高，但内容密度极大。
它解释了为什么那么多 AI 产品看起来都差不多。
Zara Zhang 前几天吐槽过，她收到的 AI 产品推广私信，定位和文案全部一模一样。
Madhu 的推文给出了原因：大家都在复用同一套 playbook。

而 Aaron Levie 的视角提供了一个对照。
他说在规模化阶段，PM 应该花大量时间和客户在一起，工程师应该理解业务目标。
AI 让两者都能多做一点对方的活，但这只是暂时的。
最终，专业分工不仅不会消失，反而会被 AI 强化。
专业人员的工具链和手艺会变得更强，产出远超业余爱好者。

这两条线放在一起，你会发现一个正在成型的职业分水岭。
Madhu 说的是"做什么"——PM 需要从执行者变成发明家。
Aaron 说的是"怎么做"——专业分工不会消失，但每个专业的工作方式会被 AI 彻底重构。
Elena 说的"IC 工作是新的职业炫耀"，恰好卡在中间。
在 AI 能执行大部分 playbook 的时代，能亲自定义新 playbook 的人，变成了最稀缺的资源。

对听众来说，这个判断有一个很直接的启发。
如果你现在的工作里有一部分是"按流程做事"——写周报、做竞品分析、跑标准化的 A/B 测试——试着问自己一个问题。
这件事的 playbook 是谁发明的？
如果答案不是你，那 AI 很快就能接手。
而如果你能定义一个新的 playbook，哪怕只是一个小领域的，你就变成了 Madhu 说的那种发明家。
