Sam Altman 昨晚发了两条长推文，系统阐述了 OpenAI 对 AI 安全和权力集中的立场。
他直接点出 AI 发展可能走向的两个坏结局。第一，人类失去对未来的控制。第二，权力过度集中，被某个人或某家公司用来强加世界观。
为了避开这两个结局，Sam 说必须走一条“窄路”。
具体做法包含几个层面。OpenAI 现在会在前沿强化学习训练前制定明确的安全论证，而不仅仅是模型发布前做安全评估。
他管这叫从“负责任的部署”转向“负责任的开发”。
同时，Sam 欢迎联邦层面建立统一的安全要求。但他强调不会等立法，现在就会做。他提到了独立审计、对齐监测，以及业界共享标准。
有意思的是他对“pacing”的定义。Sam 明确说，pacing 不是停下来，而是比原本可能的速度慢一点。
慢下来的代价是什么？是安全论证和监测带来的显著成本。但他认为这笔成本值得，因为没有任何竞争压力能成为鲁莽的借口。
不过，他留了一个尾巴。国际协调需要政府介入，但第一步是行业自己先把能做的事做了。
如果你在创业或做产品，这条窄路可能直接影响你的模型选择和合规成本。你怎么看这种“先自己干，再等政府”的路线？

先把节奏放慢一点，说一下今天最值得想清楚的一件事。
Greg Isenberg 在他的播客里聊了一个概念，叫“软件工厂”。他承认这名字有点蠢，但背后的思路很实在。
软件工厂就是五六个 markdown 文件，放在代码仓库旁边，告诉 agent 你的工作规范。
Greg 说这东西正在走红，因为 AI 编程有个信任问题。模型能写功能，但没结构的话，你就得一直盯着 agent，猜它改了啥，祈祷没搞坏别的东西。
他提出的解法，是把软件工程拆成工厂流水线。每个功能有自己的分支，多 agent 可以并行工作不打架。
建造站给 agent 写代码规则，因为“能跑”和“下个月同事能看懂”是两回事。
证明站强制 agent 展示证据。截图、视频、速度数据，必须证明功能有效，而不是嘴上说。
审查站跑一遍代码审查 agent，不合格就打回去重做。你只需要在最后合并。
Factory AI 的 CEO Matan Grinberg 也插了一句，说如果只把软件工厂当成工程工具，格局就小了。他在重建整个公司的协作基底。
Guillermo 今天也推了“技能驱动开发”这个概念，和软件工厂的思路是同一个方向。
这些声音拼在一起，能看到一个清晰的趋势。和 agent 协作的方式，越来越像和人协作。你需要规范、审查、证据，而不是一行行检查代码。
如果你正在带团队用 AI 编程，软件工厂这套方法可以立刻试。建一个 markdown 文件，写清楚你项目的代码规范和审查标准，看看 agent 的输出质量会不会变。
