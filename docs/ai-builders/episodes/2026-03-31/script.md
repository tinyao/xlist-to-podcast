Boris 是 Claude Code 的工程师。上周我们提到他因为收到用户来信走红，昨晚他换了一个完全不同的方向——发了一个 15 条的连续帖，专门分享他自己最常用但又最容易被忽视的 Claude Code 功能。开场那条推文将近两万个点赞，四万五千个书签，这个数字在过去 24 小时的所有内容里是绝对的第一。

为什么一个功能清单能有这么大的反响？因为它做了一件极少有人去做的事：把一个产品的真实高级用法，从开发者的内部视角，系统整理出来。用过 Claude Code 的人看这个帖子，基本上每一条都会产生"原来还有这个"的感觉。

我来把 15 条压缩一遍，重点说几个真正值得知道的。

首先是移动端。很多人不知道 Claude Code 有 iOS 和 Android 应用。Boris 说他大量代码是在 iOS app 上写的，不用打开笔记本。这不是"存在但没人用"的那种功能，是他主力工作流的一部分。

接下来是 teleport 和 remote-control，这两个是一对。前者运行 `claude --teleport`，把云端对话直接拉回本地继续；后者反过来，让你从手机或网页远程控制本地运行的会话。Boris 说他把"Enable Remote Control for all sessions"常驻打开了。两台设备之间无缝接力，听起来像小事，实际上是工作流里一个很真实的摩擦点。

然后是 /loop 和 /schedule。Boris 说这是"Claude Code 里最强的两个功能"。可以设定间隔时间，让 Claude 循环执行一个任务，持续最长一周。他自己在跑的有：每五分钟自动处理 code review、自动 rebase、把 PR 推上生产；每三十分钟拉一次 Slack 反馈并提 PR；每小时清理一次陈旧的 PR。他用的短语是"把工作流变成 skill 再加上 loop"，这个组合的威力比大多数人想象的要大得多。

Hooks 系统经常被忽略。它让你在 agent 生命周期的不同节点插入自定义逻辑——会话开始时动态加载上下文，每次 bash 命令前记录日志，甚至可以把权限请求路由到 WhatsApp，在手机上直接批准或拒绝。这个功能面向的是想把 Claude Code 深度集成进自己工作流的人，上限非常高。

/batch 用于大规模并行任务。先和你对话确认需求，然后把工作拆给任意数量的 worktree agent 并行完成——"几十个、几百个、甚至几千个"。适合大规模代码迁移这类天然可以并行化的工作。

还有一个值得专门一提的是 --bare 标志。默认情况下，每次运行 `claude -p`，它都会自动搜索 CLAUDE.md、settings、MCP 配置。对于非交互式场景，这些开销大多不必要。加上 --bare，启动速度可以快十倍。Boris 直接说这是当初的设计失误，未来版本会把默认值翻过来，现在先手动 opt-in。

最后是 /voice。Boris 说他大部分代码是"对着 Claude 说话写的，而不是打字"。按住空格键触发，或者在 Desktop 版点语音按钮。如果你每天和 Claude Code 打交道的时间足够多，语音输入的效率差距是真实存在的。

整个帖子里我最喜欢的细节，其实是他在结尾说的一句话："想继续讲，但不得不强制停下来了。"15 条还没讲完，还有更多。这件事本身就说明了一点——当一个工具的密度高到这个程度，官方文档永远是不够的。

说完工具本身，来看一个更大的问题。

Aaron Levie 昨晚发了一条分析帖，接着 Jeff Dean 关于"工具速度跟不上 agent 速度"的判断往下挖了一层。

他的核心观点是：现有的基础设施，从最底层开始，都是为人的速度设计的。哪怕是那些号称"机器速度"的工具，本质上也在等待某个人在系统某处发出请求。agent 以并行方式 7×24 运行，彻底改变了这个假设。

他列了几个很具体的领域。

沙箱：agent 随时需要启动编码环境，延迟要极低。现有容器的冷启动速度，是为人类偶尔触发设计的，不是为 agent 每秒触发设计的。

搜索：无论公网还是企业内网，agent 可以同时发出几百上千次搜索请求，索引和返回速度要能扛住这个规模。

支付：agent 可以做微支付，0.01 美元的交易它完全没有摩擦感，但现有支付系统的设计假设里，根本没有这个场景。

文件系统：版本控制、权限管理、多 agent 并发读写——所有这些的复杂度，都需要在新的量级上重建。

Aaron 最后说：我们正在从"为人类建软件"过渡到"为 agent 建软件"。

这个分析的价值在于它把一个很模糊的大判断，拆成了几个可以验证、可以押注的具体方向。哪些基础设施层面的创业公司会率先冒出来，接下来是值得盯住的事情。

今天还有一件事很实用，Greg Isenberg 发了一个视频，专门讲 vibe coding 项目的分发策略，被收藏了超过一千次。

他开场说："每天有超过 20 万个 vibe coding 项目被创建，但几乎没有一个能获得用户。" 代码问题越来越容易解决，但"怎么让人发现你做的东西"依然是难题。

七条策略里挑几个真正有用的说。

建 MCP server：当用户问 Claude 或 ChatGPT 一个你的产品能回答的问题时，你的工具直接出现在答案里——AI 变成了你的销售团队。这个逻辑比 SEO 更适合今天的用户行为，因为越来越多人是先问 AI 再决策，而不是先搜索。

Programmatic SEO，但要做对：用 Firecrawl 抓真实数据，加人工编辑环节。Greg 给了一个粗略估算：10000 个页面 × 30 次访问 × 2% 转化 × 10 美元 = 每月六万美元被动流量，而这些页面只需要建一次。

把产品输出做成可分享的时刻：他举的例子是 Spotify Wrapped、GitHub 贡献图、Stripe Atlas 的证书。问自己：用户完成什么之后最想截图发出去？把那个时刻设计出来，加一个预填充的分享按钮。

还有一个很直接的内容策略：把 30 分钟的语音备忘录扔给 Claude，出来五条推文、三篇 LinkedIn 帖子、一封邮件通讯和短视频素材。每周做一次，三个月后内容积累量会远超手动写的竞争对手。

Greg 的核心判断是：代码已经商品化了，现在真正的稀缺资源是分发能力。这句话不新鲜，但他给的是具体操作路径，不是泛泛的"你要做增长"。

几条快讯。

swyx 昨晚转了一项 Redpoint 的调查：46% 的企业 CIO 表示，在已有成熟软件供应商的情况下，他们愿意考虑 AI-native 初创公司。swyx 说他本来预估这个数字是 20%，实际比他想象的激进得多。企业市场的窗口期，比很多人以为的要真实。

Granola 宣布了 Series C 融资。Peter Yang 公开表态看好，理由有三：会议记录是公司里信息密度最高的上下文；他们的 agent-first API 和 MCP 设计很扎实；还有他对创始人 Chris 这个人的信任。会议笔记这个切入口，走得越来越稳。

Replit 和 RevenueCat 完成了集成，现在可以在 Replit Agent 里直接搞定移动应用内购、订阅和定价配置——包括那段通常需要几个小时的 App Store Connect 流程。

Claude Code 全线支持 GitHub Enterprise Server，包括网页端、iOS、Android 和 Code Review。自托管的企业用户不需要迁移到 github.com，直接在自己的环境里跑异步工作流。

还有一个无厘头但挺有意思的观察。Peter Yang 从韩国飞到上海，落地之后发现 ChatGPT 和 Claude 都连不上，但他看到的第一个广告是 OpenClaw 的。没有什么深刻的分析，但这个细节本身，挺能说明问题的。

今天的内容看起来是不同的事：Boris 的技巧帖、computer use 进 CLI、Aaron 谈基础设施、Greg 谈分发。

但从另一个角度看，它们在问同一个问题——工具越来越强了，接下来真正的瓶颈在哪里？

是"你知不知道这些功能"，是"基础设施跟不跟得上"，还是"做出来之后能不能被人找到"。

答案可能都是肯定的。能力的天花板在往上移，但每移动一次，新的瓶颈就会在另一个地方冒出来。这大概是接下来几年里，值得持续观察的那条线。
