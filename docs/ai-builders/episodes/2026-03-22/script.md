一个 agent 建造者的教程合集，发出来不到一天收了 7000 多个收藏。今天是 2026 年 3 月 22 日，欢迎收听 AI Builders Daily。数字本身不是重点——重点是这份清单里写了什么，又为什么这么多人想存起来慢慢看。

---

先说这份清单本身。

Thariq 昨天把他过去一年多写的所有技术文章整理成了一个合集，发了一条推文，配文只有一句："I put a lot of heart into my technical writing, I hope it's useful to you all."

到截稿时，这条推文收了超过 7100 个收藏，转发 300 多，评论 156 条。作为参考，在我关注的这个列表里，技术推文能拿到 300 个收藏就算传播不错了。7000 是一个异常高的数字，说明它触到了大量正在建 agent 的人的真实困惑。

合集里有七八篇文章，Thariq 标注了顺序，几乎就是一份 agent 建造者的学习路径。我把核心几条拆一下。

第一条，列在最前面的：Skills 是所有 agent 都会依赖的抽象层。我们前几天聊过 Claude Code 的 Skills 功能，但他这次说的是一个更底层的东西——不是"Claude Code 有个功能叫 Skills"，而是：你可以给 Claude 一份文档，让它自己学会怎么使用一个新工具或新服务，这个模式本身叫 Skills，它将来会是所有 agent 系统的通用设计模式。前两天郭宇做的 mails.dev 里有一份 skill.md，agent 看完就能自己走完整个邮箱注册流程——那就是这个模式在真实项目里的样子。

然后是那篇收藏数很高的文章："建造 agent 更像是艺术，不是科学"。这个说法和工程师的直觉是反的。工程师的本能是：把系统架构设计好，把流程定清楚，就能控制输出。但 Thariq 说，agent 的行为是涌现的——你设计了规则，但 agent 在复杂任务里怎么行动，很多时候没法完全预测。你更多是在观察它、测试它、调整它，是一个反复打磨的过程，不是一次性设计完成的工程。接受这件事，比试图把 agent 纳入传统软件的开发逻辑，要有效得多。

他自称"alpha 最高"的一篇，是关于 prompt caching 的。他补了一句：只对从头建 agent 的人真正有用。逻辑是这样的：一个 agent 系统通常有大量固定的内容——系统 prompt、工具描述、参考文档。每次调用都把这些东西重新发给模型，是有成本的。把固定内容缓存起来，成本可以压缩到原来的一小部分。成本降了，你就更愿意给 agent 更丰富的上下文；上下文更丰富，agent 的能力上限就更高。成本优化和能力优化之间，有一条大多数人没有意识到的连线。

还有两个他明确说"我愿意为之死战"的观点，都是关于 agent 架构基础的。第一：agent 应该有文件系统。用文件系统管中间状态，让 agent 能把长任务拆成可验证的步骤，检查自己做了什么，记住前面发生了什么。没有文件系统的 agent，在复杂任务里很容易"失忆"——做到一半忘了之前的决定，或者重复做已经做过的事情。第二：bash 就够了。你不需要为每个功能专门造一个新工具，agent 通过 bash 可以调用系统里几乎任何东西，而且 bash 有完整的执行记录，你能看到 agent 做了什么。他说，他跟几十家在做 agent 的公司聊过，最常说的一句话就是"多用 bash"。

最后他推荐的起点是 Claude Agent SDK，说这是他目前见过的搭 agent 最简单的方式。

这个合集最有价值的地方，不只是单独哪一条建议，而是它给出了一个有顺序的思路：先想清楚 Skills 的设计，用文件系统管状态，用 bash 做工具调用，用 prompt caching 控制成本，然后把整件事当成一门需要持续迭代的手艺——不要在一开始就试图设计出完美的架构。

7000 多个收藏，说明这份路径戳到了很多真实的困惑。

这个合集恰好是 Aaron Levie 昨天那条推文的一个很好的呼应。

Aaron 写的是 agent 技术栈的演变机制——他把它叫做"苦涩教训周期"。核心论点是：你六个月前花六个月时间打磨的东西，现在很可能已经过时了，与其修补旧架构，不如直接重置重来。

他没有停在这个泛泛的感慨上，而是描述了一个很具体的循环。

用 RAG 举例：一年多前，大量工程团队在认真搭 RAG 管道——精心设计向量检索、排序策略、信息筛选逻辑，这是真正的工程难题，有人为它投入了好几个月。现在，上下文窗口大了一个数量级，工具调用的能力也强了很多，agentic search 让 agent 可以自己决定查什么、怎么查——那套精心设计的 RAG 管道，有一部分被新能力替代了。

但这不是终点。正是因为工具调用能力提升，agent 现在能处理更复杂的任务——复杂到需要在沙箱里运行代码。于是你需要为代码执行搭新的基础设施。一个能力被"进步"掉了，但它打开了一个新的问题空间，你在新空间里要重新建一层脚手架。

他说，这个循环不会停，我们会在这个节奏里走好几年。

对于在做 AI 产品或基础设施的团队，这里面有一个很实际的推论：不要执着于你现在的技术选型是不是当下最优，而要问自己"如果这部分被下一波能力升级替代了，我们能多快切换"。架构的灵活性，比当下的最优解更重要。他用了一个很直接的说法：如果你没有这种速度和灵活性，可能真的会陷入困境。

Thariq 说建 agent 是手艺，要反复迭代。Aaron 说你的技术栈每隔几个月可能就要重置。一个是工艺层面，一个是战略层面，说的是同一件事的不同侧面。

换个方向，说一条让我今天停了最久的观察。

Zara Zhang 昨天发了一条推文，超过 1000 个点赞，107 次转发，引发了非常密集的讨论。她的原话是：几乎每一个她认识的 AI 重度用户，用了 AI 之后都变得更忙、更焦虑了，而不是更轻松。

原因她也解释了：大家以为 AI 会把生产力提高 10 倍，然后可以早点收工。结果是：AI 确实把生产力提高了 10 倍，但同时让你看到了 20 倍的可能性。以前没敢想的事，现在突然都觉得可以做——于是 todo list 不是变短了，而是以更快的速度在变长。

回复里有人说这是"AI 引发的范围蔓延"，有人说这是帕金森定律在 AI 时代的新版本：工作会自动扩展去填满一切可用资源。也有人说这是工具变强之后的正常结果，蒸汽机出来之后，人类没有减少工作，只是做了更多以前做不了的事。

两种观点都有道理。但我的观察是，Zara 戳到了一件我们谈得不多的事：使用 AI 的人的心理状态。我们的默认前提是"AI 一定让你过得更好"，但对于习惯把每一个可能性都变成行动的人来说，能做的事变多了，压力也可能跟着变多了。

这和 Karpathy 前两天在 No Priors 提到的"AI psychosis"是相关的话题。他在问的是：持续重度使用 AI 的人，思维习惯和判断力会怎么演变。Zara 在说的是：那些人的焦虑水平也在演变。同一枚硬币的两面，一个在认知层面，一个在情绪层面。

几条快讯。

Cursor 的设计师 Ryo Lu 昨天放了一个预告，域名是 cursor.com/glass，配了一张界面截图，配文只有一句"still early, but clearer now"。从截图看，是一个透明感很强的全新界面方向，和现在的 Cursor 设计语言差别相当大。没有发布时间，但放出预告通常意味着距离不远了。

郭宇的 vibelab 昨晚一口气完成了 128 个代码提交——注意这是 vibelab.live，不是前几天的 mails.dev，两个产品。这次大版本更新包括：从零搭建的 DJ 混音系统，支持多人协作用 AI 创作音乐；双人配对编程模式，每人独立沙箱终端；全站暗色模式；主播直播支持视频特效，"不想洗脸可以加马赛克"他原话；另外沙箱基础设施大幅稳定性提升，终端崩溃会自动重启。iOS 版本 TestFlight 也快来了。

Hamel 昨天说了一件已经在做的事：没有 API 的软件正在走向淘汰。他已经在用 Claude 的 Chrome 扩展，让 Claude 通过开发者控制台逆向分析网页的内部 API，然后让 agent 直接通过这些内部接口完成任务，完全绕过官方 API。他说 Claude 在做这件事上很擅长，因为能直接访问 dev console，可以分析请求结构。他把整个流程写成了 skill 文档存起来。核心逻辑是：如果一个软件不暴露标准接口，agent 会自己找到进去的路。

Peter Yang 昨天发了一条很短的观察："1M 的上下文窗口，感觉像是从 Opus 4.6 升级到了 4.7。"五百多个点赞。他在说的是：上下文窗口大小对实际体验的影响，已经达到了和模型能力升级同一个量级的感知差距。这是一个很有意思的基准说法，对于在做需要大上下文场景的人来说，值得记住。

Qwen 团队的 Junyang Lin 昨天发了一张工作截图，只有一行字："working on distillation"，1300 多个点赞，38 次转发。什么都没解释。在模型公司，发布前的沉默工作状态，往往比公告更值得盯。

最后，OpenAI 据报道计划年内把员工从 4500 人扩充到 8000 人，接近翻倍。Peter Yang 回应得很直接：他见过的经验里，在不到一年的时间里把公司规模扩大两倍，很少真的让团队跑得更快。一个值得思考的问题，尤其是在这个大家都在说"用 AI 就能以小博大"的时代。

---

今天的几件事，说的其实是同一个关于速度的问题，只是从不同角度来的。

Thariq 说建 agent 是一门手艺，需要耐心迭代。Aaron Levie 说你的技术栈可能每隔几个月就要重置，速度是生存条件。Zara Zhang 说，这种速度本身正在制造焦虑。

迭代要快，但不能失去对自己工作节奏的控制感——这是这一行现在的基本矛盾。没有统一答案。但知道这个矛盾在那里，是第一步。

Thariq 的合集、Aaron Levie 的完整推文、Zara Zhang 的原帖，链接都在 shownotes。Thariq 那份清单如果你在建 agent，值得按他标注的顺序读一遍。我们下期见。
