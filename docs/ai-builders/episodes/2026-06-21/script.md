GLM 5.2 开源带来的冲击波，会让本地模型成为开发者的日常吗？Vercel 的 CEO 说下一个热门编程语言是 Markdown，这背后是什么逻辑？产品经理这个角色，是不是也到了必须重新定义的时候？先从最让工程师兴奋的那件事开始。

开源大模型 GLM 5.2 在过去一天里，成了圈子里讨论最多的话题。这不是一次普通的版本更新，很多人直接把它叫做“本地 AI 的 ChatGPT 时刻”。

Greg Isenberg 昨天在体验之后，给出了一个很具体的评价。他说，GLM 5.2 是第一个真正能当日常主力用的开源模型。它的上下文窗口达到一百万个 token，能直接吞下整个代码库。在编码能力上，目前排到了开源模型的第一名。而且，它用的是 MIT 许可证，没有任何商用限制，可以直接通过 Ollama 或 LM Studio 在你自己的机器上跑起来。Greg 的原话是，用起来有点像 Opus 4.8，他甚至已经开始认真考虑买一台高配硬件来跑本地模型了。Box 的 CEO Aaron Levie 也从另一个角度呼应了这个趋势。他的观察是，开源权重模型正在特定任务上达到顶尖水平，在编程等领域，也在逼近最前沿的闭源模型。他认为，只要开源模型跟闭源前沿模型的差距不被拉大，哪怕只是维持在一个很小的区间，AI 应用层的价值就会被极大地释放。因为你可以用更便宜、更定制化的开源模型去优化成本，而把最复杂的规划、编排和审查工作，继续留给前沿模型。

不过，另一边也有不同的声音。Peter Yang 就说，他连 Codex 和 Claude 每个月两百美元的订阅额度都用不完，实在找不到理由去折腾本地模型。他还提到，想跑最新的 GLM 模型，需要大概 512GB 内存的机器，那相当于一台一万多美元的 Mac Studio。这个反差很有意思。如果你是个每天跟代码打交道的工程师，要不要在这个周末动手试试 GLM 5.2？

说到编程工具，Guillermo Rauch 昨天发了一条很有意思的推文。他说，下一个热门的编程语言，是 Markdown。

他给出了一个极简的 agent 结构示范。一个 agent 文件夹，里面放一个 instructions 点 md 的指令文件，再建一个 skills 子文件夹，里面放上你的专业知识说明。就这么简单。然后，用一行 vercel 命令就能部署上线。Guillermo 说，这是编程史上最容易上手的形态。而且，对于由我们人类完全定义和控制的那一代软件来说，这很可能也是最容易的终点了。他还透露了一个小彩蛋，说 Vercel 这个 agent 产品的早期原型，内部代号叫 last。既是在向 Next.js 致敬，也是在表达这个设计带给他们的那种“持久感”。你听完什么感觉？这会不会改变你对“构建 agent”这件事的认知门槛？

产品经理这个角色，在 AI 时代正在经历一场分裂。前 Google 产品负责人 Madhu Guru 昨天发了一条长文，把现在的 PM 分成了两个阵营。

一边是“老派 PM”。AI 帮他们做得更快了，产出更多的需求文档、更多的策略报告、更多的说明文件。但 Madhu 认为，这只是在加速旧的工作方式，输出的量上去了，判断力并没有本质提升。另一边，是“构建者 PM”。这群人用 AI 把自己的角色边界，扩展到了整个产品生命周期。他们会用 agent 去做市场和用户调研，直接查日志、跑数据分析，生成大量相互竞争的想法，然后从中筛选出最好的。更重要的是，他们的产出物正在从文档，变成可以交互的原型。Madhu 说，工程师对演示的反应，远比对着文档要积极得多。他的判断是，PM 这个角色正在不可逆地转向“构建者”模式。你身边的 PM 是哪一种？或者，如果你就是 PM，你最近的工作流有在变吗？

接下来这段我们多说几句。

今天值得展开聊的，是 Riley Brown 提出的一个观察。他说，当他打开 Codex 的时候，感觉自己很强大。在那个应用上做的事，分量很重。但当他打开 ChatGPT 的时候，感觉正好相反。那是一个用完即走的地方，快速进去，拿个答案就出来。所以，Riley 认为，把 Codex 和 ChatGPT 这两个品牌融合在一起，会非常困难。

这个感受在圈子里激起了不少共鸣。Zara Zhang 说得更直接。她说，大家就应该把 Codex 当成 ChatGPT 来用。自从她每天用 Codex 或 Claude Code 之后，已经很少打开 ChatGPT 了。除非是要做那种快速的网页搜索类任务，她才会用 Gemini。她的理由是，编程 agent 产出的结果，几乎总是比聊天机器人要好。Peter Yang 在前一天也分享过类似的转向。他曾经是 Claude Code 的忠实用户，但现在 Codex 赢回了他的心。原因不只是 GPT-5.5 本身很强，更在于 Codex 的浏览器和电脑操控能力。他说，他靠这两项能力构建了大量工作流，完全不用再去费力找 API 了。但有意思的是，Peter 同时也保留了 Claude Code。因为 Opus 在设计感和前端能力上，依然比 GPT 强很多。他希望这两家永远竞争下去。

这个讨论背后，其实触及了一个更深的问题。我们到底是在用 AI 工具“做事”，还是在“聊天”？Codex 这类 agent 给人的感觉，是你交付了一个任务，它在完成一件作品。而 ChatGPT 给人的感觉，是你提了一个问题，它在给一个答案。这两种交互模式带来的心理权重，是完全不同的。Riley 担心的品牌融合难题，本质上是在担心，当“做事”和“聊天”被塞进同一个入口时，用户对“做事”的那份郑重感，会不会被稀释掉。

对你的启发是什么呢？如果你在做一个 AI 产品，可能需要想清楚，你的用户是在“指派任务”，还是在“寻求对话”。这两种场景下的界面设计、反馈速度、甚至容错率，都应该不一样。如果你是一个重度用户，也许可以试试 Zara 的建议，把更多“做事”的活，直接交给 agent 模式的工具，而不是在聊天框里反复引导。你会发现，那种“我在建造点什么”的感觉，确实是聊天窗口给不了的。
