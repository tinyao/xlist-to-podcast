换个方向，说说今天最值得工程师花时间读的那条帖子。

Karpathy 昨天发了一篇很长的帖子，讲他最近怎么用 LLM 构建个人知识库。他把 token 消耗从"操控代码"转向了"操控知识"——把文章、论文、图片全部存进 raw 目录，然后让 LLM 增量编译成一个 markdown wiki，包含摘要、反向链接、概念文章。

他用 Obsidian 当前端 IDE，wiki 本身完全由 LLM 维护，他几乎不手动编辑。当 wiki 积累到足够大——他举的例子是约 100 篇文章、40 万词——就可以向 LLM agent 提出复杂问题，让它自己去研究、回答。他还补了一条延伸想象：未来每一个发给前沿 LLM 的问题，都可以自动派生出一个 LLM 团队，临时构建一整个 wiki，lint 几轮，最后输出完整报告。

Obsidian 的创始人 kepano 随后接力，提出了一个"污染防控"的角度。他建议把个人 vault 和 agent vault 分开——agent 生成的内容不要直接混进你的主 vault，否则搜索、反向链接、图谱这些功能就不再代表你自己的知识了。只有 agent 产出真正有价值的东西，再手动迁移进主 vault。

这套工作流的四个组件他也列出来了：Obsidian 本体、Web Clipper 插件、Obsidian CLI 让 agent 能调用完整功能、Obsidian Skills 让 agent 知道怎么创建 markdown 和 canvas 文件。

这件事对工程师和研究型 PM 的启发挺直接的。你现在用 AI 做研究，输出的知识有没有沉淀下来？还是每次对话结束就消失了？

另一件大事，Google 昨天同时发了两个东西，值得分开说。

Gemma 4 正式发布，Apache 2.0 开源，有两个规格：26B 的 MoE 版本和 31B 的 Dense 版本。Google 的说法是"按字节计算，当前最强开源模型"，设计目标是跑在手机、笔记本、台式机上。

Logan Kilpatrick 说这只是 Gemma 4 时代的开始。对做本地部署、边缘推理或者离线 agent 场景的团队，31B Dense 这个规格值得测一下。

同一时间，Gemini API 上线了弹性计费分层。选 flex 模式，API 成本降约 50%，但可靠性会低一些；选 priority 模式，成本涨约 80%，换来更高优先级。这个功能目前对 Tier 2 和 Tier 3 项目开放，覆盖大多数标准模型。

如果你的业务有明显的高峰低谷，这个分层设计挺实用的——低峰期跑 flex，高峰期切 priority，成本可以压下来不少。

接下来这段我们多说几句。

今天值得展开聊的，是 Lenny 播客里 Simon Willison 那段对话。Simon 是 Django 的联合创始人，也是"prompt injection"这个词的发明人，还是"agentic engineering"的普及者。他在 Lenny 的节目里说了一句话，我觉得值得停下来想一想："用好 coding agent，需要我 25 年软件工程经验的每一分。"

他的核心观点是，2025 年 11 月是一个真正的拐点。在那之前，agent 还是一个有趣的工具；在那之后，它变成了一个需要认真对待的工作伙伴。

他用了一个词叫"dark factory"——暗工厂。不是字面意义上的黑暗，而是一种自动化程度极高、几乎不需要人工干预的生产流程。他说现在的代码生产正在接近这种状态，而这对工程师群体的冲击，不是从初级工程师开始的——是从中级工程师开始的。

为什么是中级？他的解释是：初级工程师还在学习，有人愿意培养；高级工程师负责架构和判断，agent 替代不了。中级工程师做的那些"把需求翻译成代码、调试、写测试"的工作，正好是 agent 最擅长的。

他自己的应对方式是三个 pattern。第一个叫 red/green TDD——先让 agent 写测试，测试跑红，再让它写代码让测试变绿，这样你对输出有一个可验证的锚点。第二个叫 thin templates——给 agent 一个很薄的框架，而不是让它从零开始，这样输出更可控。第三个叫 hoarding——把 agent 产出的好东西存起来，建立自己的资产库，不要每次都重新生成。

他还提了一个让他睡不着觉的担忧：AI Challenger 灾难。Challenger 飞船的事故，是因为工程师知道有问题，但被压力和流程压住了，没有说出来。他担心 agent 时代会出现类似的事——系统在快速生产，但真正懂代码的人越来越少，没有人在认真审查，直到某个关键时刻出问题。

他还有一个细节挺反直觉的：他 95% 的代码是在遛狗时用手机写的。不是用 IDE，是用手机。他说这迫使他把任务拆得足够小，每一步都有清晰的验证点，反而让他的 agent 工作流更健壮。

如果你现在在用 coding agent，有没有认真想过自己的 review 流程是什么？不是"我会看一眼"，而是具体的：你怎么验证 agent 写的代码是对的？你的测试覆盖率够不够支撑这种生产速度？这几个问题，Simon 的三个 pattern 是一个挺好的起点。

Factory AI 的 CEO Matan Grinberg 发布了 Legacy-Bench，专门测试 agent 处理 COBOL、Fortran、C89 这类遗留代码的能力。结论是：这些语言对 agent 来说确实更难，但前沿模型已经能处理复杂的遗留代码任务，而且差距在快速缩小。做金融或政府系统的团队，这个 benchmark 值得关注。

OpenClaw 的 steipete 昨天转发了一个 Linux 内核安全邮件列表的数据：两年前每周收到 2-3 份漏洞报告，去年增加到每周 10 份，今年开年以来每天 5-10 份——他说唯一的变量是 AI 生成的代码报告大量涌入。大多数报告是准确的，但维护者压力骤增，不得不引入更多人手。这是 AI 辅助安全研究的另一面，值得做开源维护的朋友留意。

另外，Replit 的 Amjad Masad 昨天分享了一个案例：有人用 Replit 搭了一个定制 CRM，替代了 ServiceTitan 每月 4000 美元的订阅，第一年做到 250 万美元收入，净利润率 60%。这不是孤例——vibe coding 替代垂直 SaaS 的生意正在越来越多地成真。
