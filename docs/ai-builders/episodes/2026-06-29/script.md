Codex 桌面端的一个功能，为什么让一位资深工程师说“每天都给我带来快乐”？Guillermo 为什么说你现在需要的不是一个 LinkedIn 主页？而 Peter Yang 抛出的那个问题——云 agent 和本地模型，到底是不是矛盾的？先从最让工程师们兴奋的那件事开始。

Codex 桌面端的远程访问功能，被大量用户认为体验远超竞品。独立 AI 研究员 Hamel Husain 昨天发了一张截图，展示了他用手机远程查看所有运行中 Codex 会话的界面。他的原话是，Codex 允许你在任何设备上看到所有设备上的全部运行中会话，包括手机端。这个功能让开发者可以真正“离开电脑去摸草”，而 agent 还在后台继续工作。

Hamel 是 eval 领域的知名人物，他的感受代表了一部分硬核用户的声音。Codex 桌面端由 Andrew Ambrosino 带队，就是前两天 Lenny 在播客里深度访谈的那位。Andrew 当时提到，Codex 的周活用户已经超过五百万，从二月至今增长了六倍。更重要的是，OpenAI 内部几乎百分之百的员工都在日常使用 Codex，而且不限于工程师。

顺带说一句，Lenny 那期播客里有一个观点今天被反复引用。Andrew 说，“当任何人都能构建任何东西时，知道该构建什么的品味就成了整个游戏的全部。”这句话被 Peter Yang 和 Zara Zhang 分别转推和引用，几乎成了昨天圈内的金句。不过，真正让 Codex 桌面端拉开体验差距的，不是某一句口号，而是这种跨设备的无缝远程能力。如果你还没试过在手机上查看 agent 的工作状态，今天或许值得花五分钟体验一下。

Guillermo Rauch 昨天扔了一句很直接的话。他说，你不需要一个 LinkedIn，你需要的是你网站上一个页面，描述并链接到你交付过的所有东西。这条推文在圈子里传了一夜。Guillermo 随后又补了一句调侃，“你需要的是一个 Link，不是一个 LinkedIn。”

坦白说，这不止是一句俏皮话。结合他前一天关于“交付是一个独立于编码的技能”的论述，以及 Zara Zhang 的补充——每花一小时构建产品，就要花两小时去解释它、演示它、销售它、教别人怎么用——这三条信息串在一起，其实在讲同一件事。在 AI 大幅降低编码门槛之后，个人品牌和作品集的形式正在从简历向可交互的交付物页面迁移。如果你现在的个人主页还是一份静态简历，Guillermo 这条建议值得认真想想。

Justine Moore 昨天贴了一张美国畅销书排行榜的截图，问了一个挺尖锐的问题。她说，搞不懂为什么有人会对 AI 生成的垃圾内容变得流行感到震惊。美国最受欢迎的书现在长这样。我们本来就是一个垃圾内容的文化。

她的配图里，排行榜前列的书籍封面设计高度雷同，标题公式化。这条观察和昨天圈内关于“AI slop”的讨论形成呼应。Justine 的视角是，不要高估大众市场对内容质量的辨别力，也不要低估 AI 在规模化生产“够用”内容上的效率。这对做内容产品的团队来说，是一个挺残酷的提醒。你的用户到底是在为质量付费，还是在为可预期的消遣付费？

Peter Yang 昨天提了一个让很多人愣住的问题。他说，我正试图理清两个想法。第一，云 agent 要来了，我们应该用 VPS 而不是笔记本。第二，每个人都应该买硬件来跑本地模型。这俩难道不是有点矛盾吗？

这个问题下面吵了两百多条回复。独立开发者郭宇在另一条推文里给出了他的答案。他转发了开发者 BennyKok 的实践——一个月没用 MacBook，所有 coding agent 跑在 VPS 上，自动化跨多个 agent 协作，通过 PWA 推送通知，所有 agent 互相感知彼此状态。郭宇把这种架构叫做 VAS，虚拟代理服务器。他的逻辑是，在服务器上开发、提交、测试、构建、部署，绕开 GitHub，速度能提升十倍。

而另一边，Peter Steinberger 昨天折腾了一圈 52 寸戴尔显示器，最后还是换回了苹果 XDR。这条看似跑题的硬件吐槽，其实暗合了本地与云端之争。顶级工程师对本地开发环境的挑剔，和云 agent 的不可阻挡，并不是非此即彼。Peter Yang 自己没给结论，但他的提问本身就是一个信号。大家正在同时探索两条路，而答案可能因人而异。

先把节奏放慢一点，说一下今天最值得想清楚的一件事。

昨天 Lenny 和 Peter Yang 几乎同时发布了两期重磅播客。Lenny 访谈了 OpenAI Codex 桌面端的负责人 Andrew Ambrosino，Peter Yang 访谈了 Anthropic 的 Claude 托管 Agent 产品负责人 Jess Yan。两期节目放在一起听，你会发现一个正在发生的范式迁移。AI 产品经理的工作方式，正在被 agent 本身重塑。

起因很简单。Andrew 在访谈里详细解释了 OpenAI PM 的“区域防守”模式。传统 PM 盯功能模块，OpenAI 的 PM 盯的是模型能力边界。产品决策的核心不再是画原型，而是判断当前模型能稳定做什么、不能稳定做什么。Andrew 举了一个很具体的例子。他说 Codex 这个产品如果去年十一月发布，会彻底失败。产品完全没变，变的只是底层模型的能力。延迟了三个月，等到模型跨越了某个可靠性阈值，同一个产品就从不可用变成了五百万周活。

另一边，Jess Yan 描述了 Anthropic 内部是怎么用 agent 来做产品管理的。她的原话是，“访问代码库对我来说是最大的解锁。我不需要去戳一堆工程师问他们在做什么，我可以直接跟踪 PR，看哪些合并了、哪些部署了。”她还提到，团队会给 agent 分配过夜任务，早上醒来时 backlog 已经被清理、bug 已经被修复。她管这叫“长跑云 agent”，不受笔记本开关机的限制。

这两段叙述放在一起，信息量很大。Andrew 说的是 PM 要练“品味”——知道什么值得做。Jess 说的是 PM 要用 agent 来获得“深度”——不需要通过人就能直接感知产品的脉搏。一个是决策层的技能迁移，一个是执行层的工具替代。

对听众来说，这里有两层可以对照的东西。第一层，你自己的产品决策流程里，有多少判断是基于模型能力的静态评估，而不是动态跟踪？Andrew 说的“同产品、不同模型、不同命运”，在你的产品线上有没有类似的时间窗口？第二层，你有没有试过让 agent 直接去读代码库、跟踪 PR、合成用户反馈？Jess 描述的那种“比以往任何时候都更深度理解和交互我的产品”的状态，不是靠更勤奋的沟通达到的，而是靠绕过沟通实现的。
